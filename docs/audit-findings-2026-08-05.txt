0. CONTEXT — the bug that triggered this audit
================================================================================
apps/api/src/truegrit_api/services/appearance.py hand-maintained a Python-side
duplicate of two constant lists (AMBIENT_EFFECT_KEYS, CURSOR_TRAIL_KEYS) meant
to mirror packages/contracts/src/index.ts. The TS side and both frontends were
expanded from 15 to 50 options each; the Python copy was never updated, so the

even though the admin UI offered them and looked fully wired end-to-end.

FIXED: both Python tuples now contain the same 50 entries, in the same order,
as the TS contracts source. Verified by direct diff. Committed as 35ebfc7 and
pushed to both `testing` and `main` (fast-forward, both branches now identical
at that commit).

This audit specifically hunted for more instances of that failure class
(duplicated constants/validation drifting silently out of sync) in addition
to a general security/correctness/reliability pass.

1. CRITICAL — Cross-tenant IDOR on admin order endpoints
================================================================================
NOTE ON INTENT (confirmed with the site owner, 2026-08-05): farm owners are
*supposed* to see orders containing their own farm's products — that's the
documented, intended feature (see the seed comment quoted below). This is
NOT a "remove all order access from farm owners" bug. It's a missing
SCOPING filter: right now they see every farm's orders, when they should
only see orders that include at least one of their own farm's products.

Files:
  apps/api/src/truegrit_api/api/admin.py:5929-6040
    (list_orders_endpoint, get_order_endpoint, update_order_status_endpoint,
     refund_order_endpoint)
  apps/api/src/truegrit_api/api/admin.py:4481-4489
    (global admin search endpoint — the "orders" section of search results,
     a second call site with the identical gap)
  apps/api/src/truegrit_api/repositories/admin.py:357-413
    (AdminRepository.list_orders, .get_order_detail)
  apps/api/src/truegrit_api/repositories/admin.py:441-452
    (AdminRepository.search_orders — same missing farm filter)
  apps/api/src/truegrit_api/services/orders.py:45 (update_order_status),
  apps/api/src/truegrit_api/services/orders.py:184 (issue_refund)

Defect: these endpoints are gated only by require_permission("orders.view"
/ "orders.cancel" / "orders.refund"), which checks the permission NAME only
(apps/api/src/truegrit_api/auth/dependencies.py:107-115). Neither the
endpoints, the repository queries, nor the service functions ever filter or
check against principal.farm_id — no WHERE clause, no post-fetch check. This
is inconsistent with ~25 other admin.py endpoints (products, categories,
media search) that do apply `if principal.farm_id is not None: ...` scoping.

Confirmed exploitable: database/seeds/development.sql:213-225 grants
rol_farm_owner the orders.view permission, and the seed's own comment at
line 215-216 states: "Scoping to a single farm is enforced in the API (via
farm_members), not by these rows: orders.view here means 'orders for my
farm', not every order." That enforcement does not exist in the code I read.

I personally verified this by reading:
  - admin.py:5929-6040 (all four endpoints, no farm_id anywhere)
  - repositories/admin.py:357-413 (queries have no farm filter; compare to
    search_products() at line 415 in the same file, which DOES take a
    farm_id parameter — establishing this repo's own pattern for how farm
    scoping is supposed to be threaded through)
  - auth/dependencies.py:107-115 (require_permission is a pure permission-
    name check, no scope logic)
  - services/orders.py:45-183 and :184+ (update_order_status / issue_refund
    check actor.has("orders.cancel"/"orders.refund") but never actor.farm_id
    against the order's owning farm)
  - database/seeds/development.sql:213-225 (rol_farm_owner really is granted
    orders.view)

CORRECTION (after a deeper trace of the actual permission model): the
original write-up above said a farm-owner "can cancel or refund any order."
That overstated it. `update_order_status`'s cancel path independently checks
`actor.has("orders.cancel")`, and `issue_refund` independently checks
`actor.has("orders.refund")` — farm-owner holds neither (confirmed against
database/seeds/development.sql, and covered by the existing test
`test_refund_requires_orders_refund_permission_even_with_orders_view`), so
cancel and refund were never actually reachable by a farm-scoped principal.

The real exploitable surface was narrower but still serious:

Failure scenario: A farm-owner sub-admin (e.g. usr_farmowner in the dev seed)
signs in and calls GET /admin/orders or GET /admin/orders/{id}. They receive
every order in the marketplace — competitors' customer emails, phone numbers,
delivery addresses, totals — not just orders touching their own farm's
products (this part of the original write-up was accurate). They could also
call PATCH /admin/orders/{id}/status to push ANY order forward through its
lifecycle (confirmed → processing → completed), since that route only
requires orders.view, not a farm-ownership check — and reaching `completed`
consumes real inventory (services/orders.py:123-161), so a farm-owner could
force a competitor's order to consume that competitor's stock.

HOW TO FIX (concrete, verified against the real schema):
  - `orders` has NO farm_id column (checked database/migrations/0005_commerce.sql
    — the orders/order_items tables). A single order CAN legitimately contain
    products from multiple farms (multi-vendor cart) — order_items.product_id
    -> products.id -> products.farm_id (nullable) is the only path from an
    order to a farm. There is no per-farm sub-order split anywhere in the schema.
  - Reads (list_orders / get_order_detail / search_orders): add an
    `farm_id: str | None = None` parameter to each repository method, same
    shape as `search_products`, and filter with:
      WHERE (:farm_id IS NULL OR EXISTS (
        SELECT 1 FROM order_items oi JOIN products p ON p.id = oi.product_id
        WHERE oi.order_id = o.id AND p.farm_id = :farm_id
      ))
    (EXISTS avoids row duplication from a direct JOIN, and mirrors the
    `(? IS NULL OR p.farm_id = ?)` idiom already used in search_products —
    stay consistent with that rather than inventing a new pattern.)
    Pass `principal.farm_id` in from the three endpoints in admin.py and the
    search endpoint at line 4481-4489.
  - Writes (update_order_status / issue_refund in services/orders.py): before
    acting, run the same EXISTS check for `actor.farm_id` (when not None) and
    raise PermissionDeniedError/NotFoundError if the order has no line item
    belonging to that farm.
  - OPEN DESIGN QUESTION — needs a product decision before implementing,
    not just an engineering one: when an order contains items from BOTH the
    farm-owner's farm and another farm (multi-vendor cart), should the
    farm-owner see the WHOLE order (customer info, other farms' line items
    and prices) or only THEIR OWN line items within it? And should they be
    allowed to cancel/refund an order that includes another farm's items, or
    only their own farm's portion? The current schema has no per-farm
    sub-order/fulfilment split, so "refund only my farm's portion" would need
    new schema work; "see the whole order, act on the whole order" is the
    cheap fix but leaks other farms' data into a multi-vendor order; "see the
    whole order but can only cancel/refund when 100% of it is their own farm's
    items" is a middle ground. Pick one before implementing.

STATUS: FIXED (2026-08-05, commit follows this write-up). The owner chose
line-item-level scoping: a farm-owner sees only their own line items within
a mixed-farm order (never another farm's items or the order's true total),
and may only change an order's status when 100% of its items are theirs.

What shipped:
  - Migration 0078_order_item_farm_scope.sql: denormalized `order_items.
    farm_id`, matching the existing product_name/variant_name/sku snapshot
    pattern on that table (so a later product/farm reassignment can never
    rewrite an already-placed order's history). Populated going forward in
    services/checkout.py's `_resolve_line`/order-insert; backfilled for
    existing rows from products.farm_id (best-effort, documented caveat in
    the migration's own comment).
  - list_orders/get_order_detail/search_orders (repositories/admin.py) now
    take `farm_id`, filtering to orders with ≥1 matching line item and
    reporting a farm-scoped subtotal/total instead of the whole order's.
    get_order_detail also nulls out payment.amountMinor/refundedMinor for a
    farm-scoped read (those are whole-order figures) while keeping
    provider/status visible (needed to know "is this paid").
  - update_order_status/issue_refund (services/orders.py) gained a shared
    `_assert_farm_owns_order` guard: a farm-scoped actor may only act on an
    order when every item in it is theirs, else PermissionDeniedError.

A follow-up sweep (below, appended to this file) checked every other
admin.py resource family for the same missing-farm_id shape. Result: no
other LIVE gap — orders was the only one reachable by a seeded role. Several
other resources (reviews, bundles, subscriptions, returns, revenue/payouts)
share the identical missing-check shape but are dormant (no seeded role
holds both the relevant permission and a farm_id) — these were hardened
proactively per the owner's decision, at no behavior change for any role
that exists today (see the addendum).

2. HIGH — Coupon usage-limit race condition (TOCTOU)
================================================================================
File: apps/api/src/truegrit_api/services/promotions.py:420-429
       apps/api/src/truegrit_api/services/checkout.py:474-510

resolve_checkout_discount checks usage_limit_total / usage_limit_per_customer
via a plain SELECT COUNT(*) against coupon_redemptions. The actual INSERT
happens later, inside place_order's single db.batch(statements), with no
conditional write guarding it — contrast the inventory reservation two lines
above in the same function, which correctly uses a conditional
`UPDATE ... WHERE (on_hand - reserved) >= ?` to close exactly this race.

Failure scenario: a usage_limit_total=1 coupon is hit by two concurrent
checkout requests (two tabs, or a bot). Both read count==0 before either
inserts, both pass validation, both commit — the coupon is redeemed twice
with nothing stopping it.

3. HIGH — Inventory adjustment lost-update race; version column unused
================================================================================
File: apps/api/src/truegrit_api/services/inventory.py:47-69, 130-143

adjust_inventory (and clear_inventory_levels) reads on_hand/reserved,
computes the new on_hand in Python, then writes it back with an UNCONDITIONAL
UPDATE (no WHERE on the value/version just read). The `version` column is
incremented on every write here and in services/orders.py:92,130, but is
NEVER referenced in any WHERE clause anywhere in the codebase — a half-built
optimistic-concurrency mechanism providing no actual protection. Opposite of
checkout.py's correctly-conditional reservation UPDATE.

Failure scenario: two admin staff act on the same variant near-simultaneously
(e.g. +100 stock receipt and -20 write-off both read on_hand=50). Both
compute independently (150 and 30); the later UPDATE silently overwrites the
earlier one. inventory_movements records both deltas, but resulting on_hand
matches neither — stock count silently diverges from its own audit trail.

After fixing #1, a dedicated sweep checked every OTHER admin.py resource
family for the same missing-farm_id shape, since #1 was found by a targeted
check on orders specifically, not an exhaustive pass. Method: for every
permission `rol_farm_owner` (or any farm-scoped role) actually holds per
database/seeds/development.sql — products.*, categories.view, media.view/
upload, inventory.*, orders.view, messages.use — trace the endpoint through
its repository/service query and confirm whether `principal.farm_id` is
actually checked.

RESULT: orders was the only LIVE gap. Every other farm-holdable resource was
already correctly scoped:
  - Products, inventory, archive/restore (product branch), search (product
    branch): all correctly filter by farm_id (`_assert_product_scope`/
    `_assert_variant_scope`, `(? IS NULL OR p.farm_id = ?)`).
  - Categories, media: correctly UNSCOPED — these tables have no `farm_id`
    column at all (shared/global resources, not tenant-owned data), so
    there's nothing to scope by. Not a bug.
  - Farms CRUD, user/role admin: explicitly blocked for any farm-scoped
    principal (`if principal.farm_id is not None: raise PermissionDenied`).
  - Messages: scoped by conversation_participants membership, orthogonal to
    farms, correctly enforced.

A user question raised during this audit — "shouldn't blogs/recipes/pages
be scoped so an author only sees their own?" — turned out to already be
correctly implemented and is a DIFFERENT scoping dimension (author identity,
not farm tenancy): articles.author_user_id / recipes.chef_user_id are
enforced both in the repository list filter and via a second
`assert_owns_or_reviews` check (services/articles.py, services/recipes.py)
that 404s rather than confirms another author's post exists. No action
needed there.

DORMANT GAPS, HARDENED PROACTIVELY (owner's decision — not exploitable by
any role that exists today, but the same missing-check shape as orders):
  - Reviews (repositories/content.py ReviewRepository + services/reviews.py):
    list/count/moderate/edit/delete now check farm_id via
    reviews.product_id -> products.farm_id.
  - Bundles (repositories/bundles.py + services/bundles.py): list/detail/
    update/delete/replace-items now check farm_id via bundle_items.variant_id
    -> product_variants -> products.farm_id (all-or-nothing rule, same as
    orders, since one bundle can span farms); replace-items additionally
    rejects smuggling another farm's variant into a bundle you own.
  - Subscriptions (repositories/subscriptions.py + services/subscriptions.py):
    the shared `_get_owned_or_staff` choke-point (backs update/pause/resume/
    cancel) and both list/get endpoints now check farm_id via
    subscriptions.variant_id -> products.farm_id.
  - Returns (repositories/content.py ReturnRequestRepository + services/
    returns.py): list/detail/decide/resolve now check farm_id via
    return_requests.order_item_id -> order_items.farm_id (reusing the column
    added for #1); a return with no linked item is hidden rather than shown
    to every farm.
  - Revenue/payouts (services/revenue.py): summary/detail/payouts-list now
    scope to the caller's own farm when farm-scoped; commission-setting
    (both default and per-farm) is blocked outright for any farm-scoped
    principal (a farm setting its own commission is a conflict of interest
    regardless of "own farm only"); issuing a payout is restricted to a
    farm-scoped principal's own farm_id.

NOT touched, with reasons verified by reading the schema/migration comments
(no farm concept exists to guard, adding one would be inventing a feature
nobody asked for):
  - Coupons/promotions: 0060_coupons_and_promotions.sql's own comment says
    promotions.manage/.view are deliberately "never a role scoped to one
    operational area" — a discount campaign is a whole-marketplace decision.
  - Community discussions/content comments: customer-authored content with
    no product/farm relationship anywhere in the schema — correctly global
    moderation queues.

Verification: the full backend test suite (apps/api/tests/) stays green
with zero existing assertions changed, plus 8 new tests in
test_admin_management.py covering the orders fix specifically (farm-owner
sees only own-farm orders with correct scoped totals, gets 404 for another
farm's order, can transition their own order but gets 403 on another farm's,
a regular admin is unaffected, global search results are scoped, and the
refund ownership guard holds even when orders.refund is granted directly).
The dormant-gap hardening has no dedicated tests since no seeded role can
exercise the new farm_id parameter — the existing suite staying green with
no changes needed is the proof those guards are true no-ops today.
